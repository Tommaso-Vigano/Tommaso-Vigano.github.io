While studying NoSQL and the world beyond relational databases, I came across object-oriented databases.

They were often described as a commercial failure. This immediately made me curious: object-oriented databases appear to solve a real and widely recognised problem, so why did they never become mainstream?

This post is my attempt to understand what happened.

## What are object-oriented databases?

Object-oriented database management systems (**OODBMSs**) were developed alongside the growing adoption of object-oriented programming languages.

Their purpose was relatively intuitive: instead of translating application objects into relational tables, developers could store those objects directly in the database.

An object database could preserve concepts such as:

- Object identity
- Classes and types
- Inheritance

Consider an application containing a `Customer` object with a list of `Order` objects. In a relational database, these objects normally have to be decomposed into tables, rows, primary keys and foreign keys. Some additional mechanism must then reconstruct the objects when the application reads the data.

In an object database, the application could theoretically persist and retrieve the original object graph without translating it into a different data model.

The idea was therefore to make the database representation correspond more closely to the representation used by the programming language.

It also resembles one of the motivations behind some NoSQL technologies: instead of adapting every problem to the relational model, use a storage model that better matches the data and the application.

## Did object databases actually fail?

Before trying to explain their failure, I wanted to determine whether the premise was accurate.

Object databases still exist, so saying that they completely disappeared would be false. The more defensible claim is that they failed to become the dominant general-purpose database technology.

One indication of this can be found in the [DB-Engines ranking](https://db-engines.com/en/ranking).

![Comparison between leading database systems and an object-oriented database]({{ '/assets/images/db-engines-ranking.png' | relative_url }})

In the snapshot used for this comparison, Oracle—the highest-ranked database—has a score of 1119.79. InterSystems IRIS, the highest-ranked system in the comparison with object-oriented capabilities, has a score of 2.07 and occupies the 123rd position overall.

There is an important qualification: InterSystems IRIS is not exclusively an object database. It is a multi-model system that also supports relational, document and key-value representations. The highest exclusive object database is even lower.

Moreover, the DB-Engines score should not be interpreted as a direct measurement of installations or market share. Its [ranking methodology](https://db-engines.com/en/ranking_definition) combines signals such as search-engine results, job offers, professional profiles and mentions on technical websites.

## A solution to the object–relational mismatch

The limited adoption of object databases may initially seem surprising because they address a genuine problem.

Most modern applications are written using object-oriented languages, while most databases organise information through relations and tables. Moving data between these two representations requires some form of translation.

This phenomenon is commonly called the [object–relational impedance mismatch](https://en.wikipedia.org/wiki/Object%E2%80%93relational_impedance_mismatch).

Object-relational mapping tools automate part of this work, but they do not eliminate the underlying difference. Developers still encounter problems.

If this mismatch is real, and object databases were designed to remove it, why did they not replace relational databases?

My initial personal hypotesis relies on these concepts:

## 1. Relational databases already had an ecosystem

When commercial object databases began to appear, relational databases already had a considerable advantage.

Organisations had invested in relational systems, SQL expertise and integrations. Replacing the database would therefore have meant replacing much more than a storage engine.

SQL was also becoming a shared language across products. Although implementations differed, developers could transfer a large part of their knowledge between systems.

Object databases frequently exposed language-specific or vendor-specific interfaces. Choosing one could create a much stronger dependency on a particular database, programming language or object model.

The challenge was consequently not just that developers had to learn something new. Companies would have had to abandon an established and increasingly standardised ecosystem.

## 2. Object databases lacked a durable common standard

The Object Data Management Group attempted to create a common object database standard through the ODMG specification.

However, object databases never achieved the level of interoperability that SQL provided for relational systems. Products continued to differ in their object models, query languages and programming interfaces.

When the ODMG dissolved in 2001, the object database market was left fragmented. Without a widely adopted standard, switching products could require substantial changes to both the stored data and the application code.

This made object databases a riskier long-term choice, particularly for large organisations concerned about portability and vendor lock-in.

## 3. Application objects are not necessarily the best permanent data model

An object model is designed for the needs of a particular application.
A database often outlives that application.

Application classes  change frequently. Properties are renamed, classes are divided and inheritance hierarchies are redesigned. 

The separation imposed by relational databases can be inconvenient, but it also creates a boundary between application code and persistent data and this boundary can be valuable.

## 4. Navigating objects and querying data are different problems

Object databases are well suited to following known relationships.

If an application already has a `Customer` object and needs to retrieve its orders, navigating directly from one object to another is natural.

However, organisations also need to ask questions that were not anticipated when the application was designed:

- Which customers bought a particular product during the last six months?
- Which regions produced the highest average order value?
- Which accounts show an unusual combination of activities?

Relational databases are particularly effective at these ad hoc, set-oriented queries. SQL describes the required result without forcing the user to specify a path through an object graph.

An object model optimised for navigating individual objects is not automatically an ideal model for reporting, aggregation or analysis across many objects.
